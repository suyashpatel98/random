# Crucible: a task-qualification platform for agentic post-training

> Users submit agentic tasks (SWE-bench- and Terminal-Bench-style). The platform decides which tasks are
> valid and *useful for RL training* by running cheap automated checks first, then k agent attempts
> in sandboxes. Every trajectory is recorded and shown in a viewer. The platform's main output is a
> qualified task set. Training itself is out of scope.

One project that starts small and gets deeper. Each stage takes one layer of the system
apart, makes a prediction from first principles, measures it, improves it, and publishes the result.

---

## 1. Why this project

- **It looks like a production system.** RL labs run very large numbers of sandboxed rollouts. Task
  quality, sandbox throughput, and inference efficiency are all problems those teams are actively working on.
- **It covers the whole stack** in one system: Linux internals, storage, sandboxes (gVisor), hypervisors
  (Firecracker/Kata), Kubernetes, and LLM serving (vLLM/SGLang).
- **The load is real.** Sandbox load is generated by the platform itself, and the agent traffic it sends
  to the inference server is a real workload, not a synthetic benchmark.
- **It calls for architectural decisions**, not only features. Positioning: *principal-level systems
  engineer with AI-infra depth*.

## 2. Theses (what the blog series argues)

1. **The main metric is valid trials per GPU-hour.** TTFT, TPOT, sandbox cold start, verifier time,
   and queueing are all parts of it. When a sandbox is slow, the GPU sits idle.
2. **Serving is a storage-hierarchy problem.** Data is either *immutable and shared* (model weights, task
   images) or *mutable and per-instance* (KV cache, per-trial sandbox state). The two need different
   designs at every tier: object store → network → NVMe → page cache/DRAM → GPU memory.
3. **A useful task is one the model solves *sometimes*.** With GRPO-style RL, a task where all k attempts
   pass, or all k fail, gives zero advantage and therefore no learning signal. The platform should output a pass-rate
   estimate with uncertainty, plus a reason for every failure.
4. **An infrastructure failure must never be counted as a model failure.** An OOM, a pull timeout, or a
   flaky verifier that gets recorded as "agent failed" corrupts the training signal.

## 3. Non-goals

- Writing an inference engine. Use vLLM or SGLang.
- Training models, or building a new coding agent. Use Harbor's agents (`mini-swe-agent`, `terminus-2`, …).
- Replacing Harbor. Harbor is the trial runner. Crucible is the platform around it.

## 4. Architecture

```
                 ┌──────────────────────────────────────────────────────────────┐
  submit task ──▶│ Submission API  ──▶  Task store (S3/MinIO: bundles, images)  │
                 └──────────────┬───────────────────────────────────────────────┘
                                ▼
                 ┌──────────────────────────────┐     ┌─────────────────────────┐
                 │ Qualification pipeline        │────▶│ State DB (Postgres)     │
                 │ (task state machine, funnel)  │     │ tasks, trials, verdicts │
                 └──────────────┬───────────────┘     └─────────────────────────┘
                                ▼
                 ┌──────────────────────────────┐
                 │ Trial orchestrator           │  queueing, k-attempt policy,
                 │ (drives Harbor jobs)         │  retries, failure classification
                 └───────┬──────────────┬───────┘
                         ▼              ▼
        ┌────────────────────────┐   ┌──────────────────────────────────────┐
        │ Sandbox layer          │   │ Model gateway (OpenAI-compatible)     │
        │ (Harbor BaseEnvironment│   │ tags every request with trial_id/turn │
        │  pluggable backends)   │   │  ├─ hosted API (dev)                  │
        │  ├─ docker (dev)       │   │  └─ self-hosted vLLM/SGLang (GPU)     │
        │  ├─ agent37 (gVisor)   │   └──────────────────────────────────────┘
        │  ├─ crucible-k8s       │
        │  │   runc/gVisor/Kata  │
        │  └─ firecracker        │
        └───────────┬────────────┘
                    ▼
        ┌────────────────────────┐   ┌──────────────────────────────────────┐
        │ Trajectory store       │──▶│ Review UI: ATIF trajectory viewer,   │
        │ (ATIF JSON + artifacts)│   │ failure triage, accept/reject         │
        └────────────────────────┘   └──────────────────────────────────────┘

  Observability: OpenTelemetry spans per trial phase + Prometheus/Grafana
  (platform, sandbox, and engine metrics joined on trial_id)
```

**Key design choices**

- **The sandbox backend is pluggable** through Harbor's `BaseEnvironment`. Moving from Docker to Agent37 to
  our own Kubernetes layer to Firecracker never touches the platform code, and each backend acts as the
  baseline for the next.
- **The model gateway is the single point where inference is observed.** Every request carries
  `trial_id`, `attempt`, and `turn`, so inference timings can be joined with sandbox and phase timings. That join is
  what makes "trials per GPU-hour" measurable.
- **One trace per trial.** The spans are: `queue_wait → sandbox_ready → agent_loop{model_call, tool_exec}* →
  verify → collect → teardown`. Every later optimization is judged against this breakdown.
- **Language:** Python for the Harbor-facing pieces (Harbor is Python). Go for the Kubernetes controllers
  and the sandbox service, when those stages arrive.

### Task state machine

```
SUBMITTED → STATIC_OK → ORACLE_PASS → NOP_FAIL → JUDGE_OK → PROFILED → TRIAGED → ACCEPTED
     └──────────┴────────────┴───────────┴──────────┴───────────┴─────────┴──→ REJECTED(reason)
                                                                          └──→ NEEDS_REVIEW
```

Every rejection carries a typed reason: `provenance`, `structure`, `oracle_fails`, `nop_passes`,
`spec_verifier_mismatch`, `grader_issue`, `flaky`, `too_easy`, `unsolved_broken`, `unsolved_hard`.

## 5. The qualification funnel (cheapest check first)

| # | Check | Cost | What it catches |
|---|-------|------|-----------------|
| 1 | Provenance | ~0 | Duplicates or near-duplicates of known benchmarks, contamination signals, licence/source metadata |
| 2 | Structure | ~0 | Harbor task layout, `task.toml` schema, the Dockerfile builds, the tests write a reward file |
| 3 | Oracle run (`oracle` agent) | sandbox only | The reference solution must pass. If it doesn't, the environment or tests are broken |
| 4 | Null run (`nop` agent) | sandbox only | Doing nothing must fail. If it passes, the verifier is too weak or the answer is already in the image |
| 5 | Oracle rerun ×N | sandbox only | Flaky verifiers (timing, randomness, network) |
| 6 | LLM judge | tokens (small) | Spec/verifier mismatch, underspecified instructions, tests that check things the instruction doesn't ask for, instructions that give the answer away |
| 7 | Difficulty profiling | tokens (large) + sandbox | k agent attempts produce a pass-rate estimate |
| 8 | Failure triage | tokens (small) + human | For 0/k and low-pass tasks: did the model fail at reasoning, or is the task broken? |

**Difficulty policy (adaptive k):** run k=4. 4/4 → `too_easy`. Mixed → candidate; extend to k=8 to
tighten the estimate (Wilson interval). 0/4 → triage, optionally escalate to k=8. Accept when the pass-rate
interval lies inside a target band (start with 0.1–0.7 and tune it). Only *agent* failures count toward the
pass rate. Infra failures are retried and reported separately.

**Triage** uses an LLM summarizer over the ATIF trajectory: where the agent diverged, and whether the
failure is attributable to the task. Then a human reviews it in the viewer. Accepted failures are labeled
`legit_reasoning_failure`.

## 6. Data: seed tasks + deliberately broken tasks

There are no real users, so we create the ground truth ourselves:

- **Seed set:** Terminal-Bench 2.0 plus a SWE-bench subset (via `harbor datasets list`). Start with 20–50 tasks.
- **Mutation operators.** Each produces a known-bad copy of a seed task:
  - `leak_solution`: copy the solution into the image
  - `weaken_verifier`: the tests always pass, or assert almost nothing
  - `spec_drift`: the instruction asks for X, the tests check Y
  - `contradiction`: the instruction contradicts the tests
  - `flaky_test`: time- or randomness-dependent assertion
  - `env_rot`: missing or unpinned dependency, so the build breaks or behaves differently over time
  - `giveaway`: the instruction spells out the fix
- **Evaluation:** precision and recall of each funnel stage against the mutation labels, plus the
  funnel's yield and its cost per rejected task.

## 7. Metrics

**Platform**
- Valid trials per GPU-hour (**primary**), cost per accepted task, funnel yield per stage
- Check precision and recall (against mutations), infra-failure rate, retry rate

**Trial breakdown** (from traces)
- Queue wait, sandbox-ready time (p50/p99), model time vs tool-execution time, verifier time, teardown
- GPU idle fraction caused by sandbox/tool time

**Sandbox**
- Cold start (image pull/unpack/start), warm start, fork time, memory per sandbox, sandboxes per host
- Syscall-heavy overhead (build and test suites) for runc vs gVisor vs microVM
- Page-cache and storage behavior (shared image layers, CoW overhead)

**Inference** (self-hosted)
- TTFT, TPOT/ITL, end-to-end latency, goodput under a TTFT+TPOT SLO
- Prefix-cache hit rate, KV-cache usage, running/waiting queue depth, preemptions, batch size
- Bytes of KV held across tool calls, and the cost of recomputing vs retaining it

**Method rule for every post:** predict first (back-of-envelope: memory bandwidth, IOPS, syscall
counts), measure, then explain the gap. Record the hardware, software versions, date, and scripts.

## 8. Stages

Each stage contains: **build → experiments → post(s) → done when**.

### Stage 0: End-to-end MVP *(Mac, Docker, hosted API model)*
- **Build:** task submission (CLI is enough), Postgres state, MinIO task store, funnel checks 1–4,
  k trials via Harbor on Docker, ATIF trajectories stored, a minimal viewer, verdicts.
- **Model gateway v0:** a thin OpenAI-compatible proxy that logs per-request timing with `trial_id`.
- **Experiments:** run the seed set end to end, and measure the cost and time per task.
- **Post:** *"Anatomy of a task-qualification pipeline: where the time and money go."*
- **Done when:** one command qualifies 20 tasks and the viewer shows every trajectory.

### Stage 1: Funnel correctness and statistics
- **Build:** checks 5–8, the mutation generator, adaptive k, typed rejection reasons, failure classification
  (infra vs agent vs verifier).
- **Experiments:** precision and recall per check, how much cheap checks save before token spend, judge
  accuracy, how many trials adaptive k saves.
- **Posts:** *"Most broken RL tasks can be caught without spending a single token"* and *"Which tasks
  actually teach: pass rates, zero-advantage groups, and why 0/k is ambiguous."*
- **Done when:** mutation recall and precision are measured for every stage.

### Stage 2: Self-hosted inference and the agent workload *(rented GPU sessions)*
- **Build:** a vLLM/SGLang deployment script (one GPU, 24–32B-class open coding model), a Prometheus scrape,
  and the gateway pointed at it. The whole session is scripted (provision → run → collect → destroy).
- **Experiments:** characterize agentic traffic (context growth per turn, prefix sharing across k attempts
  and turns, length of idle gaps during tool calls). Prefix caching on vs off. Concurrency vs TTFT/TPOT/goodput.
  Roofline prediction vs measured TPOT.
- **Posts:** *"Agent rollouts are not chat: characterizing RL rollout traffic"* and *"Prefix caching
  under k-attempt rollouts."*
- **Done when:** a joined dashboard shows the trial phases and the engine metrics for the same run.

### Stage 3: Sandbox cold start and image storage *(Linux box)*
- **Build:** instrument sandbox startup. Add a local registry and image cache, and try lazy-pull
  snapshotters (stargz / SOCI / Nydus) and EROFS-based images.
- **Experiments:** where startup time goes (pull, unpack, overlay mount, process start), layer dedup
  across tasks, page-cache sharing across concurrent sandboxes, behavior on cold vs warm nodes.
- **Post:** *"Where a sandbox's first 30 seconds go."*
- **Done when:** p50/p99 sandbox-ready time is broken down by phase, with one change that improves it, measured.

### Stage 4: Warm fork, so k attempts share one setup
- **Build:** set up and install dependencies once, then fork k times. Compare overlayfs upper-dir copies, reflinks
  (XFS/btrfs), CRIU checkpoint/restore, and Agent37's fork as an external baseline.
- **Experiments:** time per fork, memory and disk overhead per fork, effect on trial throughput.
- **Post:** *"Copy-on-write for RL rollouts: forking a warm sandbox k ways."*

### Stage 5: Our own sandbox layer on Kubernetes
- **Build:** a `crucible-k8s` Harbor environment backed by a Go sandbox service or controller (with a CRD
  for sandboxes). Use RuntimeClass to choose runc / gVisor (runsc) / Kata per task trust level. Add
  resource limits and network policy.
- **Experiments:** isolation vs density vs overhead on real build and test workloads (syscall-heavy),
  scheduling latency, packing density.
- **Post:** *"runc vs gVisor vs Kata for untrusted agent tasks: what isolation costs."*

### Stage 6: MicroVMs
- **Build:** a Firecracker backend (directly, or through Kata). Add snapshot/restore of a warmed VM, and memory
  overcommit/ballooning.
- **Experiments:** boot vs restore time, lazy memory restore, sandboxes per host at fixed RAM, noisy neighbors
  (cgroups, PSI).
- **Post:** *"Restoring a warm microVM in milliseconds, and what that buys an RL platform."*

### Stage 7: KV cache across tool calls *(GPU session)*
- **Question:** while the sandbox runs tests, should the engine keep the trial's KV cache in GPU memory,
  move it to CPU/NVMe, or drop it and recompute?
- **Experiments:** measure tool-call gap distributions from stage 2 traces, the cost of retaining vs
  recomputing the KV cache, and the effect on goodput under memory pressure. Use engine features
  (CPU offload, KV connectors / LMCache-style tiering) where available.
- **Post:** *"Your agent is thinking, your GPU is waiting: the KV cache during tool calls."*

### Stage 8: The control plane that couples sandboxes and GPUs
- **Build:** a rollout scheduler that is aware of both sandbox capacity and inference capacity. Add admission
  control, backpressure, and pre-warming sandboxes ahead of demand. Add failure handling (infra vs agent),
  retries, and drain.
- **Experiments:** trials per GPU-hour before and after. Calibrate a simple discrete-event simulator with the
  measured numbers to reason about 100–1000-node fleets.
- **Post:** *"Designing a rollout platform for trials per GPU-hour"* (the series capstone).

## 9. Environments and budget (cap: $100)

| Resource | Used for | Est. spend |
|---|---|---|
| Mac + Docker | Stages 0–1, all development | $0 |
| Hosted LLM API (open-weight coding model) | Stages 0–1 trials | ~$15 |
| Agent37 | External gVisor baseline, fork baseline | $5 starter credit |
| Rented GPU, hourly, scripted sessions | Stages 2 and 7 | ~$35 |
| Linux box with KVM (dedicated/bare metal, ~1 month) | Stages 3–6 | ~$45 |

*Prices are estimates. Check current rates before you rent anything.* Notes:
- Do Linux work in a local VM first (Lima/UTM), and rent the box only for the measurements you publish.
- Firecracker and Kata need `/dev/kvm`. Most cheap cloud VMs don't expose nested virtualization, so plan on bare metal.
- Never leave a GPU running. Every session is a script with a hard teardown.

## 10. Blog post template

1. **The problem in operator terms:** what it costs (GPU-hours, dollars, corrupted signal).
2. **The mechanism:** name the real components (syscalls, snapshotters, engine schedulers).
3. **The prediction:** back-of-envelope from first principles.
4. **The measurement:** method, hardware, versions, date, and links to scripts.
5. **The gap:** why the reality differs from the prediction.
6. **The decision:** the architectural choice and its tradeoffs.
7. **What changes at 1000×:** reasoning plus simulation, clearly labeled as such.
8. **Limits:** what this single-node experiment does *not* show.

## 12. Risks

| Risk | Mitigation |
|---|---|
| Token cost of SWE-style trials | Cheap checks first, adaptive k, small seed set, measure cost per trial before scaling up |
| Self-hosted model too weak (everything 0/k) | Pick tasks in the model's range, use Terminal-Bench tasks of varied difficulty, compare against a stronger API model |
| GPU sessions wasted on debugging | Debug on CPU/llama.cpp or the API first. GPU only runs finished scripts |
| Vendor black boxes (Agent37) limit depth | Use them only as baselines. The depth comes from stages 3–6 on our own stack |
| Scope creep | Each stage ends with a published post before the next one starts |

## 13. Open decisions
